# wlk — Design Document

**Version:** 0.1 (draft)
**Language:** C
**Interface:** CLI only (no TUI)

---

## 1. Purpose

`wlk` is a personal project tracker for tracking multiple side projects. It combines lightweight structured state (per-project todo lists with measurable completion) with a narrative log (small dated entries recording what happened and how the project felt).

It is deliberately **not** an issue tracker. There are no IDs on todo items beyond display convenience, no states beyond done/not-done, no assignees, priorities, or labels. Experience has shown that heavyweight tracker formats don't survive contact with hobby workflows.

Design philosophy: *walks, not sprints.* Progress is measured as ground covered per list, remembered as a story in the log.

## 2. Core Principles

1. **Central storage.** All data lives in a single location under the user's home directory (e.g. `~/.wlk/` or `$XDG_CONFIG_HOME/wlk/`). Projects do **not** scatter `.db` files into working directories. Nothing to gitignore, nothing to lose track of, nothing leaking into group repos.
2. **Plain-text friendly.** Storage is human-readable text, or SQLite behind a single file — either way, one file you can back up by copying it. If plain text: one project per section or per file inside the central directory; format must survive manual editing.
3. **Every project is identified by a short stable ID** assigned at `init` time (e.g. incrementing integer or short slug). IDs are how all commands refer to projects.
4. **Export is a first-class citizen.** Any project's full state (description, lists, items, logs) must be exportable to JSON and Markdown at any time. This doubles as a de-facto backup and integration path.
5. **No ambient processes.** `wlk` runs, does one thing, exits. No daemon, no hooks.

## 3. Data Model

```
Project
├── id           (unique, immutable, assigned at init)
├── name         (human-readable title)
├── description  (free text, settable/editable)
├── created      (date)
├── status       (active | paused | finished | archived)
├── lists[]      (ordered todo lists)
│   ├── name
│   └── items[]
│       ├── text
│       └── done  (bool)
└── logs[]       (append-only)
    ├── date     (timestamp at creation)
    └── text     (free-form short entry)
```

Notes:

- Completion percentages are **computed, never stored.** A list's completion = done items / total items. Project completion = weighted or simple average across lists (simple average is the v0 recommendation; see §7).
- Logs are append-only. Editing or deleting log entries is out of scope for v0.
- Lists have no ID requirement internally; they are referred to by name or index within a project. (Rename operations should rewrite references, hence list *names* are stable keys in v0.)

## 4. Commands (v0 surface)

| Command | Arguments | Effect |
|---|---|---|
| `wlk init` | `<name>` | Create a new project, assign ID, print it. |
| `wlk ls` | — | List all projects: ID, name, status, overall completion %. |
| `wlk desc` | `<id> [text]` | Show or set the project description. |
| `wlk list` | `<id> add <listname>` | Add a todo list to a project. |
| `wlk item` | `<id> <listname> add <text>` | Add a todo item to a list. |
| `wlk item` | `<id> <listname> done <index>` | Mark an item done (toggle with `--undo`?). |
| `wlk stat` | `<id>` | Full status report (see §5). |
| `wlk log` | `<id> [text]` | Append a log entry; with no text, open `$EDITOR`. |
| `wlk log` | `<id> --show [n]` | Print last n log entries (default all). |
| `wlk export` | `<id> --format=json\|md [--out=<file>]` | Export project (see §6). |
| `wlk status` | `<id> <status>` | Change project status (paused, finished, …). |

Design conventions:

- Consistent verb-first subcommands; `<id>` always comes first.
- Human output to stdout, errors to stderr, meaningful exit codes (0 ok, 1 usage, 2 not-found, 3 storage error).
- `wlk` with no arguments prints a short cheat sheet, not an error.

## 6. Export

- `--format=json`: faithful dump of the data model in §3. Schema should be documented and stable enough that future-you can parse it with `jq`.
- `--format=md`: rendered document with headers for description/lists/logs; suitable for pasting into a repo README or wiki if the project someday grows into one.
- Default output to stdout; `--out` writes to a file. Export is read-only and never modifies state.

## 7. Open Questions (decide before implementation)

1. **Plain text vs. SQLite for the central store.** Plain text: greppable, diffable, hand-editable, and parsing is a genuine C learning exercise (a bounded one). SQLite: robust concurrency and querying for free. Recommendation: plain text for v0, structured so a future SQLite backend behind the same loader functions is possible.
2. **Overall completion weighting.** Simple average across lists, or weighted by item count? Item-weighted is fairer (a 12-item list shouldn't equal a 2-item list) but harder to eyeball. Decide once, document it.
3. **ID scheme.** Incrementing integers (simple, stable) vs. slugs (memorable, renames hurt). Integers recommended.
4. **Log entry granularity.** Timestamps to the day, or to the minute? Day-level keeps exports clean; minute-level helps reconstruct sessions later. Consider day-level storage with day+time ordering preserved within a day.
5. **Concurrency.** v0 can ignore it (single writer assumed), but the locking story should at least be "atomic write via temp file + rename" so a crash can't corrupt the whole store.

## 8. Non-Goals (v0)

- Reminders, notifications, scheduling.
- Multi-user anything.
- Inter-operation with git (auto-detecting repos, linking commits).
- Configurability beyond a fixed storage path.
- Editing or deleting log entries.
- Dependencies between todo items.
